04. Arquitetura em um olhar

Monólito modular: cada módulo é dono do seu domínio; comunicação por api.*/IDs/eventos, sem FK cross-module.

ArchUnit verdesem dependência nova
sharedkernelIDs, TenantContext, eventos e vocabulário RBAC (Resource/Action/Scope/AccessTarget/VisibilityScope)
iamTenant, User, auth, papéis e concessões com escopo
departmentDepartment, orçamento mensal (BudgetLimit), ModelPolicy
aigatewayProvider, Model, tentativas duráveis, completion
chatConversation, Message, recibo privado
agentpoliciesKnowledgeDocument, agentes, recuperação segura
observabilityUsageRecord, custo real, BudgetStatus calculado
frontendExpress/EJS + proxy /api + telas por escopo

Allowlist que o ArchUnit protege

iam→sharedkernel
department→sharedkernel + iam.api
observability→sharedkernel + iam.api + department.api
chat / agentpolicies→aigateway.api + iam.api
proibido→domain/application/infrastructure de outro módulo
Orçamento é meta; custo é fato.
O department é dono do orçamento mensal. O observability é dono do custo real e calcula o status na leitura. A ligação é o contrato DepartmentBudgetQuery.budgetFor/budgetsFor, por ID — sem FK e sem cópia local.

Fluxo do orçamento até a tela

PUT /departamentos/{id}/orcamentos/{mes}→ MonthlyBudget (V016)→ BudgetResolution→ QueryBudgetStatus→ custo real (SQL [from,to))→ OK / ALERTA / EXCEDIDO / SEM_ORCAMENTO
linha do mês› monthly_budget padrão (limiar 80)› sem orçamento (nunca zero)

06. Conexão front ↔ backend e telas

O browser fala same-origin; o BFF Express serve EJS e encaminha /api/* para o Spring. Sem token no servidor Node.

páginas 200XSS corrigidoD2 pendente
Browser→ Express/EJS→ proxy /api/*→ Spring Boot→ PostgreSQL
JWT no header→ TenantContextFilter→ RBAC/targeting→ escopo aplicado no backend

O front nunca envia tenant_id. Ele só escolhe filtros permitidos; toda decisão de escopo, papel e alvo é refeita no backend. /me/permissoes serve para esconder menus e botões, não para autorizar.

07. Segurança e multi-tenancy

Invariantes que valem para todo endpoint e que os ITs provam nos dois sentidos: acesso permitido e acesso proibido.

tenant do JWTSQL com tenant_id403/404 corretos
✓
Tenant sempre do contexto
TenantContextHolder; nunca de body/query do cliente.
✓
Queries nativas tenant-aware
Todo SQL de uso/custo inclui tenant_id = ? explicitamente.
✓
Escopo antes da query
visibilityFor + isAllowed; filtro fora do escopo → 403.
✓
Outro tenant não existe
Recurso de outro tenant → 404, sem revelar existência (inclui convite F6).
✓
Teto de CHAT é SELF
Nem TENANT_ADMIN amplia acesso a conversas; admin só não tem CHAT.
✓
Sem segredo/conteúdo em log
Prompt/resposta/documento/token não entram em log nem em módulo analítico.
✓
XSS em notificações
Mensagens/e-mails passam por textContent, não por HTML.
✓
ArchUnit
Falha para import interno cross-module ou dependência fora da allowlist.
